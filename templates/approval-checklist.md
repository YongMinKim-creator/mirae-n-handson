# 승인 체크리스트 v1 · 2회차

버전: v1 (팀 기준 반영)

오늘 바뀐 점
- "충분하다 · 적절하다 · 지나치게 많지 않다" 같은 판단 문장을 예/아니오 문장으로 바꿨다.
- 치명 이슈 · 범위 밖 변경 · 테스트 · 컨벤션의 팀 결정을 기준에 넣었다.
- 컨벤션 위반은 반려(계층 규칙 · 빈 catch · System.out), 경고(네이밍)로 나눴다.

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려. 모든 항목은 예/아니오로 답한다.

## 심각도 정의

- **치명** — 아래 여섯 가지 중 하나라도 있으면 치명이다. 1건이라도 있으면 반려.
  1. 비밀값 노출
  2. 데이터 손실
  3. 인증 우회
  4. SQL 문자열 조립
  5. 개인정보(학생 식별자 · 이메일) 노출
  6. 서버 입력 검증 누락
- **경고** — 지금 고치지 않아도 동작하지만 다음 변경에서 사고가 될 가능성이 있는 문제. 컨벤션의 네이밍 위반이 여기에 속한다. 경고만 있으면 승인하고 목록으로 남긴다.
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 모듈의 테스트 명령을 실제로 실행했다(실행하지 않고 통과라고 쓰지 않는다).
- [ ] 실행 결과에 실패 · 오류가 0건이다.
- [ ] 새로 추가한 public 메서드마다 그 메서드를 호출하는 테스트가 있다(getter · setter · 생성자 · record 접근자는 제외).
- [ ] 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없다.

## 2. 치명 이슈 0건

- [ ] 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처에 리터럴로 들어 있지 않다.
- [ ] SQL 을 문자열로 이어 붙여 만드는 곳이 없다(파라미터 바인딩 사용).
- [ ] 요청에 없는 데이터 삭제 · 덮어쓰기 코드가 없다(있다면 요청에 그 내용이 명시돼 있다).
- [ ] 인증 · 권한 검사를 건너뛰거나 약화시키는 변경이 없다.
- [ ] 로그 · 응답 · 예외 메시지에 학생 식별자(`STU-…`) · 이메일 · 토큰 값을 원문으로 넣는 코드가 없다.
- [ ] 새로 추가 · 변경된 엔드포인트의 외부 입력(경로 · 쿼리 · 본문)마다 서버 측 검증(타입 · 범위 · 길이 · 허용 목록)이 있다.

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었다(없으면 판정하지 않고 먼저 묻는다).
- [ ] 변경 파일 목록의 모든 파일이 요청 문장으로 설명된다.
- [ ] 요청 문장과 무관한 변경은 같은 파일 안의 import 정리뿐이다(메서드 추출 · 로그 변경 · 포맷 정리는 범위 밖이다).
- [ ] 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면 요청에 포함돼 있었다.

## 4. 컨벤션 준수

- [ ] 팀 `CLAUDE.md` 의 코딩 컨벤션과 금지 사항을 대조했다(`convention-check` Skill 이 있으면 그 결과를 쓴다).
- [ ] 컨트롤러에서 Repository · SQL 을 직접 호출하는 곳이 없다(위반 시 반려).
- [ ] 예외를 잡고 아무 처리 없이 넘기는 곳이 없다(위반 시 반려).
- [ ] `System.out.println` · `console.log` 같은 임시 출력이 남아 있지 않다(위반 시 반려).
- [ ] 클래스 · 메서드 · 변수 이름이 팀 네이밍 규칙을 따른다(위반 시 경고, 반려 사유 아님).

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 네이밍 경고만 있으면 컨벤션은 충족으로 표시하고 경고로 남긴다. 코드는 수정하지 않는다.
