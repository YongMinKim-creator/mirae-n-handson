# 레거시 모듈 문서화

## 원칙
- **분석 대상 폴더(`legacy/**`)와 `db/**` 의 파일은 읽기만 한다.** 쓰는 곳은 `docs/<모듈명>/` 뿐이다.
- 코드에서 확인한 것만 적는다. 주석과 코드가 다르면 코드를 따르고, 불일치를 비고에 남긴다.
- 근거를 줄번호로 댈 수 없으면 문서의 "미확인" 절로 보낸다.

## 0. 인자 · 모듈명
- `$ARGUMENTS` 첫 번째 = 모듈 경로, 두 번째(선택) = 범위 제한(예: `search.php 만`, `등록 흐름`).
- `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다. 표에 없는 경로면 멈추고 묻는다.

  | 모듈 경로 | 모듈명 |
  |---|---|
  | `legacy/item-bank-php` | `item-bank` |
  | `legacy/assignment-thymeleaf` | `assignment` |
  | `legacy/grade-mssql` | `grade` |

## 절차 — 단계마다 파일로 저장한 뒤 다음 단계로 넘어간다
1. **계획 제시.** 파일 목록(`vendor/` 등 외부 코드 제외)을 훑고, 읽을 파일 · 스키마 위치(`db/mariadb/init/` 또는 `db/mssql/init/`) · 단계 · 산출물을 먼저 보여 준다. 범위 제한이 있으면 여기서 반영한다.
2. **진입점.** 요청을 받는 파일 · 컨트롤러 메서드 · 프로시저를 찾아 `ARCHITECTURE.md` 의 "모듈 개요 · 폴더 구조 · 진입점" 절을 쓰고 저장한다.
3. **의존 관계.** 호출 그래프(mermaid)와 호출 표(호출하는 쪽 `파일:줄` → 호출되는 쪽 정의 `파일:줄`)를 `ARCHITECTURE.md` 에 덧붙여 저장한다. 끝에 "미확인 목록"을 둔다.
4. **데이터 흐름.** 테이블 목록 · 관계(mermaid erDiagram) · 관계별 근거 · 읽기/쓰기 위치(SELECT · INSERT · UPDATE · DELETE)를 `ERD.md` 로 저장한다.
   관계마다 **구분** 열에 `선언`(스키마 FK · 제약을 `파일:줄` 로 인용) 또는 `추정`(FK 없이 JOIN · WHERE 조건 · 컬럼 이름에서 짐작)을 적는다. `추정` 은 erDiagram 에서 점선(`..`)으로 그린다.
5. **비즈니스 규칙 후보.** 조건 · 검증 · 정렬 · 제외 · 상태 전이 규칙을 아래 형식으로 `BUSINESS-RULES.md` 에 저장한다. 맨 앞 "먼저 볼 것"에 주석 · 코드 불일치와 이관 시 결정이 필요한 항목을, 끝에 "뽑지 않은 것 · 주석만 있는 것"과 "매직 넘버" 표를 둔다.
6. **표본 점검 추천.** 사람이 직접 코드와 대조할 규칙 3개를 추천한다(아래 참고).

## 산출물
- `docs/<모듈명>/ARCHITECTURE.md` — 개요 · 폴더 구조 · 진입점 · 의존 관계 · 미확인
- `docs/<모듈명>/ERD.md` — 스키마 출처 · 테이블 · 관계(선언 / 추정 구분) · 읽기/쓰기 위치 · 미확인
- `docs/<모듈명>/BUSINESS-RULES.md` — 규칙 후보 · 뽑지 않은 것 · 매직 넘버
- 근거 표기: 레거시 코드는 모듈 폴더 기준(`search.php:215`), 스키마는 저장소 루트 기준(`db/mariadb/init/01-schema.sql:70`).

## 규칙 형식
~~~markdown
### BR-01
- 규칙: (한 문장. 조건과 결과를 함께 쓴다)
- 근거: `파일:줄번호`, `파일:줄번호`
- 근거 코드:
  ```php
  (근거 줄을 그대로 인용)                // 파일:줄번호
  ```
- 확신도: 확실 | 추정
- 비고: (주석과 다른 점, 스키마 제약, 이관 시 고려할 점)
~~~
- 확신도: **확실** = 조건문 · SQL 로 확인, **추정** = 이름 · 주석 · 언어 동작에서 짐작(실행해 보지 않음).

## 하지 말 것
- **존재하지 않는 함수 · 파일 · 테이블 · 컬럼을 쓰지 않는다.** 이름을 적기 전에 Grep 으로 정의 위치를 찾고, 찾은 `파일:줄` 을 그대로 적는다.
- **호출 방향을 뒤집지 않는다.** "A → B" 는 A 의 본문에서 B 를 부르는 줄을 인용할 수 있을 때만 쓴다. include · import 만 있고 호출이 없으면 "참조"로 적는다.
- **코드에 없는 규칙을 만들지 않는다.** 주석 · 화면 문구 · 컬럼 이름 · 일반적인 업무 상식(중복 금지, 상한 등)만으로는 규칙을 세우지 않는다. 그런 것은 "뽑지 않은 것 · 주석만 있는 것" 표로 보낸다.
- 요청된 범위에 해당 코드가 없으면(예: 수정 기능 없음) 규칙을 지어내지 말고 "코드 없음"이라고 적는다.
- 인용한 코드와 줄번호가 실제 파일의 그 줄과 같은지 저장 전에 다시 읽어 확인한다.
- `legacy/**` · `db/**` · `characterization/**` 를 고치지 않는다.

## 마지막 단계 — 사람이 표본 점검할 규칙 3개
- 답변 끝에 3개를 추천하고, 각각 규칙 ID · 근거 `파일:줄` · 고른 이유를 적는다.
  1. **가장 그럴듯한 규칙** 1개 — 너무 당연해서 검토 없이 믿기 쉬운 규칙(틀렸을 때 가장 늦게 발견된다).
  2. 확신도 **추정** 인 규칙 중 이관 영향이 가장 큰 것 1개.
  3. 주석 · 코드 불일치 또는 매직 넘버가 걸린 규칙 1개.
- 점검 결과를 받으면 `BUSINESS-RULES.md` 끝에 "검증 이력"(규칙 ID · 결과 · 틀린 유형)을 추가한다.
