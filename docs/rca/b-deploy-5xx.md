# b-deploy-5xx 장애 원인 분석 (RCA) — 1~3절 (가설 표까지)

> **진행 상태: 작성 중.** 이번에는 "1. 수집 범위", "2. 타임라인", "3. 가설과 검증"의 가설 표까지만 썼다. 코드 대조, 반증 시도, 판정, 요약, 수정안(4절 이후)은 하지 않았다. 코드 · 설정 · 원본 로그는 수정하지 않았다.

## 1. 수집 범위

- 대상: `incident-logs/b-deploy-5xx/` 의 파일 3개 (2026-09-17 하루 중 09:00 ~ 14:39)
- 이 절은 범위 확정만 다룬다. **원인 추측은 하지 않는다.**
- 집계 방법: `wc` · `head` · `tail` · `grep -c` · `grep -n` 과 분 단위 집계용 `grep -o … | uniq -c`(건수만)를 썼다. 파일을 통째로 읽지 않았다.

### 2.5 로그에서 찾지 못한 것

아래는 "사건이 없었다"가 아니라 **아래 키워드로 찾았을 때 이 묶음에 없었다**는 뜻이다.

- `nginx-error.log` 가 이 묶음에 없다. 502 8건의 upstream 오류 문구(`connect() failed`, `upstream` 등)를 확인할 수 없다.
- 배포 전 7건의 500(배포 41)과 배포 후 39건의 500(배포 42 · 43)이 **다른 배포 ID 를 쓰는 것**은 확인했으나, 로그만으로 두 배포의 학급이 같은지는 모른다. 로그에 `distribution 41` 의 학급이 찍힌 줄이 없다.
- 배포 41 · 42 · 43 의 `assignment_id` 를 알려 주는 DB 조회 로그가 없다. `Assignment 9` 를 참조하는 배포가 무엇인지는 로그에 없다.
- `redistributed` INFO 뒤 ERROR 로 500 을 낸 요청의 DB 커밋 여부(재배포가 저장됐는지)를 알려 주는 줄이 없다.
- 학급 1 에서 14:34:45 이후 요청이 없는지, 왜 14:34 에 멈췄는지 알려 주는 줄이 없다. 로그가 14:39:58 에서 끝난다.
- 재시작 · 롤백 시도 흔적: 13:41:48 이후 `Started` 외에는 없다. 롤백(`v1.4.1` 이미지 재기동, `deploy-history.md:22`) 흔적은 이 묶음에 없다.
- 설정 변경 흔적(`reload|refresh|maximumPoolSize`)은 찾지 않았다(2절 범위 밖).

### 2.6 이 단계의 한계

- `app.log` 의 스택 트레이스는 첫 블록과 앱 프레임(`com.example`) 집계만 봤다. 블록별 전문 비교는 하지 않았다.
- 5xx 건수는 access 기준이고 app ERROR 와 건수가 일치한다(39 · 7). 요청 단위 대응(같은 요청의 access 줄과 app 줄)은 시각으로만 맞췄다.
- 사용자 영향의 크기(502 8건 · 500 39건이 몇 명에게 미쳤는지)는 이 단계에서 판단하지 않았다.

## 3. 가설과 검증

- 이 절은 **가설 표까지만** 작성했다. "실행 결과" 열과 판정은 비워 두었다. 반증 시도(로그 · 코드)는 다음 단계에서 한다.
- **증상과 원인을 구분한다.** 가장 많이 나온 오류는 `Entity … Assignment … identifier value 9 does not exist` 를 담은 500(46건, 2절)이다. 이것은 "무엇이 터졌는가"일 뿐이다. 아래 가설은 "왜 학급 1 의 재배포에서만, 배포 후 39건이 모두 이 오류가 됐는가"와 "502 는 무엇 때문인가"에 답하려는 것이다.
- 줄번호 `app:N` · `access:N` · `deploy:N` 은 2절과 같은 파일 줄이다.

### 3.5 H4 — 인프라 · 배포 방식 (502 8건은 재기동 중단)

| 항목 | 내용 |

### 3.6 H5 — 트래픽 · 클라이언트 (500 후 재호출 증폭)

| 항목 | 내용 |
|---|---|
| 1. 가설 | 교사 화면(교사단말A)이 500 을 받은 뒤 같은 재배포 요청을 반복(3회 묶음)해 500 건수를 키웠다. 각 요청은 `redistributed` INFO 를 남긴 뒤 500 이 되므로, 재배포가 실제로 저장되는 구조라면 같은 배포가 중복 재배포됐을 수 있다. 사용자 영향과 데이터 부작용의 범위를 정하는 가설이다(원인 가설은 아니다). |
| 2. 지지 근거 | ① 500 39건이 같은 클라이언트의 3회 묶음으로 몰려 있다(`access:17155` · `17170` · `17181`, 10~25초 간격). ② 같은 클라이언트가 배포 전에도 41 에 3회 묶음으로 호출했다(`access:3150` · `3162` · `3174`). ③ 학급 1 의 성공 INFO 는 39건이고 500 은 39건으로 1:1 이다(2.4절). ④ 배포 43 의 성공 INFO 는 33건, 42 는 24건으로 한 배포에 반복 기록이 쌓여 있다(`app` 의 `redistributed` 줄 집계, 하루치). |
| 3. 반증 조건 | ⓐ 재배포 `INFO` 뒤 트랜잭션이 롤백돼 DB 에는 저장되지 않는다(중복이 없다). ⓑ 재요청이 500 때문이 아니라 사용자의 새 입력이다(사유 문구가 매번 다르다). ⓒ 재요청 간격이 자동 재시도 패턴(고정 간격)이 아니다. |
| 4. 확인 방법 | `awk` 로 같은 클라이언트 · 같은 URL 의 500 직후 재요청 간격 집계(`grep -n '<교사단말A 의 IP>' …`) / `app` 의 `reason=` 값이 묶음마다 같은지 확인 / (4절 이후) `DistributionService.redistribute` 의 `@Transactional` 경계 · `save` 위치 확인 / DB 의 배포 이력 행 수 확인(운영 담당에게 요청) |

### 3.7 가설 사이에서 가르는 관찰 (판정이 아니라 다음 확인의 순서)

- H1 ↔ H2: `Assignment` 9 존재 여부(3.3 ⓐ)와 `listByClass` 코드(3.2 ⓒ)를 둘 다 보면 "코드가 이력을 읽다 터진다"와 "데이터가 깨져 있다"를 구분할 수 있다. 둘이 같이 참이면 H1 은 경로(직접 원인), H2 는 조건(배경 원인)이다.
- H2 ↔ H3: 개발 DB 시드에 배포 41 계열 데이터가 있는지 보면 "테스트가 못 잡은 것"과 "시드가 현실과 달랐던 것"을 가를 수 있다.
- H4 는 별개 사건이라 위 사슬과 독립으로 확인한다(nginx 에러 로그가 필요하다).
- 모든 가설 공통 한계: `nginx-error.log` 가 없고(2.5절), 응답 시간 필드가 없으며, 학급 · `assignment_id` 가 로그에 없다(2.5절). 확인 방법은 이 빈칸을 채우는 쪽으로 골랐다.
